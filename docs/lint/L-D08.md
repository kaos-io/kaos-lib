# L-D08 NoCudaForGpuStep

**Level: warning.** A step asks for a GPU, but its image shows no CUDA support, or its plain base image does not set the NVIDIA driver path.

## What it checks

The step is `gpu=True` in `pipeline.py`, its base image is not a CUDA image (no `cuda`, `nvidia`, `pytorch` or `tensorflow` in the name) and neither the Dockerfile's `pip install` lines nor `pyproject.toml` / `requirements*.txt` name a GPU library (torch, tensorflow, jax, cupy, ultralytics ...). Second case (rule set 1.3.0): the step is `gpu=True`, its base image is not a CUDA image, and no `ENV LD_LIBRARY_PATH=...` line in the Dockerfile names `/usr/local/nvidia`. A step that has neither CUDA support nor the path gets the first message only. This check is a heuristic: it searches text.

## Why it matters

The step gets a GPU on its node and cannot use it: it trains on the CPU and holds a GPU (and its cost) for nothing. A pip `torch` wheel bundles CUDA, so `python:3.12-slim` plus `torch` is fine; `python:3.12-slim` alone is not.

The platform adds `/usr/local/nvidia/lib64:/usr/local/nvidia/lib` to `LD_LIBRARY_PATH` and `/usr/local/nvidia/bin` to `PATH` for a GPU step on its own GPU machines, and fails the step in its first second if the driver cannot be reached. So the second warning is about every other environment: your own GPU workstation with the NVIDIA container runtime, another cluster, a local `kaosctl step run`.

## How to fix

Depend on a GPU library, or use a CUDA base image such as `nvidia/cuda:12.2.0-runtime-ubuntu22.04`. On a plain base image, add

```dockerfile
ENV LD_LIBRARY_PATH=/usr/local/nvidia/lib64:/usr/local/nvidia/lib
ENV PATH=/usr/local/nvidia/bin:${PATH}
```

(a plain python image has neither variable set, so nothing of the image's own is lost). If the step does not need a GPU, remove `gpu=True`.
